# 00 · 总体设计 — 终态定义、范围与分层

> 状态：Phase 0 冻结稿（v0.0.1）。本文是全仓库设计的锚点；其余设计文档
> 均从本文推导。修订需在 CHANGELOG 记录并更新版本号。

## 1. 终态定义

一句话定位：**独立的飞书流式卡片平台（Gateway + SDK），任何 agent 通过
统一事件协议接入。**

对照前代（hermes-lark-streaming v2.1.x），"一步到位"的判据是四条：

| 维度 | 前代（v2.1.x） | 本项目（终态） |
|------|----------------|----------------|
| 契约 | 文本启发式编码（`{emoji} {tool}…`、`💬`、围栏块） | 结构化事件协议 v1（JSON 信封）；文本模式仅作适配器侧兼容输入 |
| 引擎 | 2306 行单文件，状态以旗标组合隐式表达 | 显式回合状态机，每个转移单一所有者，守卫条件显式注册 |
| 宿主依赖 | core 存在宿主 ABI 泄漏（`SendResult` try-import `gateway.platforms.base`） | 零宿主依赖字面成立：编排层及以下禁止任何宿主 try-import |
| 接入形态 | in-process 继承（hermes 专属优化）+ bridge 骨架 | 库形态 + 网关形态双形态，同一 core，接入方一律走协议 |

## 2. 范围（0.x）

### 范围内

- 单租户、单飞书应用凭证的流式卡片引擎与网关
- 回合生命周期管理（流式 / 澄清暂停续流 / 定稿 / 回合外投递）
- 竞态防御全套（见 02-engine）
- 卡片模板 Schema + 主题 token
- 事件协议 v1 与三种传输绑定（stdio / HTTP / WS）
- hermes（形态 A）与 openclaw（形态 B）两个参考接入方

### 范围外（防"平台化烂尾"，1.0 前一律不做）

- 多租户 / 多飞书应用隔离
- 鉴权体系（凭证即配置，不做用户体系）
- 持久化（状态全部内存态 + 看门狗/GC 收口；崩溃即降级原生，消息不丢）
- **入站接管**（收消息、媒体下载、群门控、cron 调度——一律由宿主 agent
  自留。本平台只做出站侧。这是与前代最大的范围裁剪）
- 多语言 SDK（协议稳定后另行发布；0.x 先 Python 核心 + 协议文档）

## 3. 分层架构与依赖方向

```
┌──────────────────────────────────────────────────────────┐
│ 接入层 adapters/                                          │
│   hermes / openclaw / codex / …                            │
│   职责：原生出站流 → 协议事件映射；凭证与设置供值          │
├──────────────────────────────────────────────────────────┤
│ 协议层 protocol/                                           │
│   事件信封编解码、握手协商、frame.ack 回执、文本兼容模式   │
├──────────────────────────────────────────────────────────┤
│ 编排层 engine/                                             │
│   回合状态机、竞态守卫、定时器（看门狗/续期/合并/GC）、    │
│   per-chat 降级、回合外旁路                                │
├──────────────────────────────────────────────────────────┤
│ 渲染层 renderer/                                           │
│   卡片 Schema v1 + 主题 token → 纯函数渲染 CardKit JSON    │
├──────────────────────────────────────────────────────────┤
│ 传输层 transport/                                          │
│   CardKit REST 客户端、限频冷却、序列自愈、重试、字节预算  │
└──────────────────────────────────────────────────────────┘
```

依赖红线（违反即架构回归）：

1. 自上而下单向依赖；下层永不 import 上层。
2. 编排层及以下**零 agent 感知**：不得出现任何 agent 名词（hermes/openclaw）
   的分支逻辑；agent 特异性只存在于接入层与配置值。
3. 零宿主 ABI try-import：出站回执是本协议的 `frame.ack`，不是宿主类型。
4. 渲染层是纯函数：`render(state, theme) → dict`，无 IO、无时钟、无随机。

## 4. 部署双形态（同一 core）

| 形态 | 适用 | 进程模型 | 事件路径 |
|------|------|----------|----------|
| **A · 库** | Python agent | 与 agent 同进程 | agent 直接构造事件对象 → `engine.submit(event)` → 同步返回 `ack` |
| **B · 网关** | 非 Python agent | 常驻独立进程 | agent 经 stdio / HTTP POST /v1/events / WS 投递 JSON → 编解码 → 同一引擎 → `frame.ack` 回执 |

形态 B = 形态 A + server shell（协议编解码 + 传输端点），编排层无感知。

## 5. 设计纪律（重申，违反需用户裁决）

0. **可靠性第一（最高优先级，2026-11-20 用户裁决）**：本框架的第一目标
   是**与飞书的交互一定不能出问题**——飞书交互可靠性 > 功能丰富度 >
   通用性优雅度。冲突时先保可靠性；必要时动用真实飞书环境验证
   （授权已获，见 02-engine §10）。框架设计到位后，前代历史问题
   （重复建卡/误封/会话过期等）应当结构性不复存在，而非依赖补丁。
1. **设计先行**：Phase 0 全部规格冻结后才进入 Phase 1 编码。
2. **知识冻结**：前代全部生产伤疤先落地为
   [`04-knowledge-freeze.md`](04-knowledge-freeze.md) 的怪癖表 / 事故档案 /
   验收基线；新引擎的行为验收以该基线为准。
3. **架构动而语言不动**：语言保持 Python（决策记录：瓶颈在网络不在 CPU；
   接入方经协议说话，实现语言对 Node 系 agent 不可见）。
4. **消息永不丢**：任何卡片路径失败 → `ack.verdict=fallback` → 接入方走
   原生投递。此红线在协议层与引擎层双重保证（见 01-protocol §7、
   02-engine §7）。

## 7. 长期演进：协议是永久契约，适配层是脚手架

定位声明（2026-11-20 用户裁决）：

- **LSEP 协议（01-protocol）是面向第三方的公开标准**：任何 agent 官方
  仅凭协议文档即可实现投递端（零 SDK、零本仓库代码）——文档必须
  自包含、字段语义完备、传输绑定明确。
- **现阶段**（插件名气不够、官方未采用）：`adapters/` 由本项目代做
  一层适配（hermes / openclaw 等），让接入方零成本获得流式卡片能力。
- **未来**（官方按协议原生接入）：适配层整体退役（可丢弃的脚手架），
  协议与核心引擎永续。

工程含义：任何协议变更都必须假设接入方不依赖本仓库代码；
适配层不得向协议文档泄漏内部实现细节。
